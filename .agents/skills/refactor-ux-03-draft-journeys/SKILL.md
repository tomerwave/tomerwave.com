# Draft the Desired User Journeys

Source: this repository's `refactor-ux` chain.

## When to use it

Immediately after `refactor-ux-02-confirm-goal` in the same session — never standalone.

## The playbook

1. **Name the desired journeys explicitly** — the paths through the product you want to exist,
   for the ICP confirmed in step 2, not a transcription of whatever the current navigation
   happens to do.
2. **Give the model real latitude to propose**, not just take dictation. Ask what journey it
   would design for this ICP and this goal, then react to that proposal.
3. **State each journey as a sequence a specific user takes to a specific outcome** — entry point,
   the steps between, the moment it succeeds — not a feature list.
4. **Flag journeys the current product actively fights against.** Those are the refactor's real
   targets, more than any single screen's visual polish.
5. **Do not build mockups yet.** Journeys get pressure-tested by the ICP panel first.

## Exit gate

- [ ] the desired journeys are written down as concrete sequences, not feature bullets
- [ ] you've reviewed them and they reflect what you actually want, not a safe default

Once both hold, invoke `refactor-ux-04-icp-panel-journeys`.

## Why this matters

"Refactor the UI" without named journeys turns into surface-level restyling — new colors on the
same broken paths. Drafting the journeys first is what gives the rest of the chain something
concrete to redesign toward.
